HOW THESE MODULES TOUCH EACH OTHER
----------------------------------

Seven couplings that are not visible from inside a single module. The first one
crosses between us, so it needs a conversation rather than a merge.


1. JOBS DEPENDS ON NODES, THROUGH THE INTERFACE            (cross-owner)

   OrphanRequeueSweep already imports nodes.HeartbeatStore. J9 asks
   isAlive(nodeId) for each known node and drains the inflight list of any that
   died. It must bind to the INTERFACE, never to RedisHeartbeatStore, which the
   file's own comment states in capitals.

   CONSEQUENCE: Shahyar can build J3, J5, J7 and J8 immediately, but J9 cannot
   be finished or tested until Averi's N6/N7 land. Agree the HeartbeatStore
   signature before either of us starts and it stops being a blocker.


2. THE MONGO HEALTH CHECK IS SWITCHED OFF                  (silent failure)

   application.yml sets management.health.mongo.enabled: false. That was correct
   when asdb took over telemetry and left Mongo with zero consumers, because the
   indicator reported DOWN for a database nothing used and dragged
   /actuator/health down with it.

   CONSEQUENCE: four of the six modules bring Mongo back: N4/N5, J5, O5, V4.
   Whoever lands the first of them must flip that flag back to true in the same
   commit. Miss it and health reports green while Mongo is down, which an
   orchestrator will believe.


3. JOBS AND EGRESS BOTH PUBLISH THROUGH REALTIME           (shared bean)

   JobService, OrphanRequeueSweep and EgressService all import
   realtime.RealtimePublisher. The implementation (StompRealtimePublisher)
   already exists from Module 1, so nothing here is blocked.

   CONSEQUENCE: the interface is now shared across both owners and two modules.
   Changing its signature breaks the other person's build, so treat it as frozen
   unless we both agree.


4. INJECTING A BARE EXECUTOR FAILS TO START                (startup trap)

   JobService (J8) and AuditService (V6) both want an Executor. The application
   already failed to boot once for exactly this: four candidate beans and no way
   to choose. TelemetryService was fixed with @Qualifier("telemetryExecutor").

   CONSEQUENCE: qualify the injection point in both modules. An unqualified
   Executor parameter takes the whole application down at startup, not at the
   call site.


5. RULE 5: STORAGE LIVES BEHIND A SEAM                     (architecture rule)

   Nothing outside a store implementation may import a Mongo API. That rule is
   what let the entire telemetry backend swap to asdb by changing one property,
   with TelemetryService and the controller untouched.

   CONSEQUENCE: every new module keeps the pattern: an interface (NodeStore,
   JobStore, ConfigStore, AuditStore) plus an implementation. Services depend on
   the interface only.


6. THREE MODULES SHARE REDIS                               (shared infra)

   Nodes uses it for heartbeats (N7), Jobs for the priority queue and inflight
   lists (J7), Overrides for the config read cache. Redis health is deliberately
   left ENABLED, unlike Mongo, because those beans are live.

   CONSEQUENCE: key namespaces must not collide, and Redis being down now fails
   two owners' modules at once. J7's claim is specified as a single atomic
   BLMOVE; the file warns against decomposing it, since a non-atomic claim hands
   one job to two nodes.


7. ASDB AND MONGO NOW COEXIST                              (storage split)

   Telemetry writes go to asdb over its binary protocol. Every other module in
   this list is specified against Mongo. Both will be running.

   CONSEQUENCE: asdb needs its own process for telemetry to work at all:

       asdb telemetry.db --port 7070 --abp-port 7071 \
            --ttl telemtry_snapshots.receivedAt=7d

   The TTL flag is not optional, and there is no error if it is missing, only a
   collection that grows forever. The protocol itself is documented in
   PROTOCOL.txt in the asdb repo.
